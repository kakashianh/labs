# GIS database schema (KAN-13)

## Database and migrations

- PostgreSQL 16 with PostGIS 3.5, provided by the root `docker-compose.yml` service.
- SQLx embedded migrations are stored in `backend/src/db/migrations/` and applied automatically at backend startup by `backend::db::run_migrations`.
- The KAN-13 migration enables PostGIS and creates the base GIS tables. The database role used to run migrations must be allowed to create the PostGIS extension.
- Start the stack from the repository root with `docker compose up --build`. To inspect the extension after startup:

```sql
SELECT PostGIS_Full_Version();
```

## Data model

```text
regions (1) ─────────── (N) buildings
  Ben Thanh AOI             OSM building footprints
```

### regions

| Column | Type | Rules | Source mapping |
|---|---|---|---|
| id | UUID | PK, generated by `gen_random_uuid()` | Internal identifier |
| code | VARCHAR(64) | NOT NULL, UNIQUE | Stable project key; use `ben-thanh-aoi-1km` for the sample |
| name | VARCHAR(255) | NOT NULL | AOI GeoJSON `properties.name` |
| description | TEXT | nullable | AOI GeoJSON `properties.area_note` |
| boundary_method | VARCHAR(64) | NOT NULL | AOI GeoJSON `properties.boundary_method` |
| source_reference | TEXT | nullable | AOI GeoJSON `properties.source_reference` |
| boundary | geometry(MultiPolygon, 4326) | NOT NULL, GiST | AOI GeoJSON geometry |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL, default NOW() | Database timestamps |

The source GeoJSON geometry is MultiPolygon (one feature), even though older KAN-6 prose described it as Polygon. The database follows the actual GeoJSON geometry.

### buildings

| Column | Type | Rules | Source mapping |
|---|---|---|---|
| id | UUID | PK, generated by `gen_random_uuid()` | Internal identifier |
| external_id | VARCHAR(128) | NOT NULL, UNIQUE | `building_id`, preserve `way/{id}` or `relation/{id}` |
| osm_type | VARCHAR(16) | NOT NULL, CHECK | `osm_type`, only `way` or `relation` |
| osm_id | BIGINT | nullable | Numeric-string `osm_id` for relations |
| osm_way_id | BIGINT | nullable | Numeric-string `osm_way_id` for ways |
| region_id | UUID | NOT NULL, FK → regions.id | UUID of the imported AOI |
| name | TEXT | nullable | OSM `name` |
| building_type | TEXT | nullable | OSM `building` |
| footprint | geometry(MultiPolygon, 4326) | NOT NULL, GiST | GeoJSON feature geometry |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL, default NOW() | Database timestamps |

The migration validates the OSM identifier shape: a `way` row has `osm_way_id` and no `osm_id`; a `relation` row has `osm_id` and no `osm_way_id`. The checked KAN-6 sample has 431 features, 424 way IDs and 7 relation IDs; all non-null IDs are numeric strings and fit BIGINT.

## CRS and spatial operations

- Store source geometries as EPSG:4326 to avoid changing the KAN-6 coordinate contract.
- Do not interpret planar measurements on EPSG:4326 geometry as meters.
- For metric area/distance, cast to geography or transform to a suitable projected CRS such as EPSG:32648.
- Use `ST_Intersects` with the GiST indexes for spatial filtering.

## KAN-14 import contract

1. Insert or upsert the single AOI into `regions` first, using stable `code = 'ben-thanh-aoi-1km'`; retain the resulting UUID.
2. Import each building with `region_id` set to that UUID.
3. Use `external_id` as the idempotency key for upsert; never use feature order/FID as identity.
4. Preserve `way/` and `relation/` namespace in `external_id`.
5. Convert non-null `osm_id` and `osm_way_id` strings to BIGINT; keep the unused identifier column NULL.
6. Insert geometry as MultiPolygon with SRID 4326.
7. Do not invent height, floors, population, occupancy, or epidemiological attributes.
